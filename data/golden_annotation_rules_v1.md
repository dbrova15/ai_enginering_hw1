# HardwareResearch AI — правила розмітки Golden Set v1

**Статус:** погоджений набір робочих правил для наступної перевірки 10 еталонів; кожен окремий еталон залишається `needs_human_review`, доки його не звірено повторно за цими правилами.  
**Контракт:** наявний `src/schema.py`; схему і `prompts/v1.txt` не змінюємо.  
**Основний принцип:** еталон містить лише відомості, які підтверджуються вхідним TXT. Типове знання про обладнання не є джерелом доказів.

## 1. Одиниця розмітки і межі

- Один `expected` описує **головний предмет конкретної статті**, не всі речі у світі, які вона згадує.
- Для `project` / `tutorial`: фактично використані, змонтовані, підключені або прямо перелічені як складові описаної реалізації елементи. Те, що автор планував, відхилив, назвав лише альтернативою чи можливим доповненням, не включати.
- Для `review` / `comparison`: конкретні моделі, фізичні вузли або вимірювальні прилади, які є предметом огляду чи безпосередньо порівнюються/застосовуються під час описаних вимірювань. Не додавати випадкові приклади периферії або можливих застосувань.
- Для `theory`: апаратні елементи **фактично описаного експерименту чи реалізації**, якщо такі є. Згадані як аналогія платформи виключати.
- Метадані сайту (`Плати:`, `Категорії:`) не є доказом того, що плату використано в проєкті. Можна використовувати як контекст тільки без приписування участі.
- Не домислювати відсутні властивості, бренди, протоколи або моделі на підставі загальних технічних знань.

## 2. `components`: що включати

### Включати

1. **Функціональні апаратні складові:** плати, мікроконтролери, датчики, реле, двигуни, батареї, перетворювачі, індикатори, дисплеї, клапани тощо, якщо вони відповідають межам розмітки з §1.
2. **Електронні деталі**, якщо джерело прямо називає їх частиною схеми (`R4`, `C1`, `VT3` тощо). Можна об’єднувати **тільки однорідні елементи з тією самою явно описаною роллю**: наприклад, `Резистори R1, R2, R3` для одного ланцюга встановлення порогів. Елементи з різними ролями не об’єднувати.
3. **Конструктивні та монтажні елементи**, прямо необхідні для відтворення й перелічені в складі/переліку деталей: корпус, шасі, конкретно вказані типорозміри гвинтів, роз’єми, перемички. Не намагатися вгадувати неописану кількість проводів, припою, клею тощо. Звичайні витратні матеріали без конкретної специфікації не робити обов’язковими компонентами.
4. Для оглядів — **прямо підтримувані пристрої та апаратні вузли, характеристики яких оглядаються**, а також явно зазначене випробувальне обладнання, якщо його використано для вимірювання.

### Не включати

- Відхилені конструкції, лише пропоновані майбутні аксесуари, випадкові приклади використання.
- Зовнішні цільові пристрої, не включені фізично до описуваної системи (наприклад, модель 3D-принтера, для якого підібрано кріплення), якщо вони є лише контекстом.
- Мови програмування, бібліотеки, IDE, сервіси, браузери — вони належать до `software_tools`, коли справді використані/предметно описані.
- Номери контактів, швидкості, граничні значення, назви алгоритмічних змінних — це не апаратні компоненти.
- «База системи» і «вимірювальний пристрій» як **додаткові дублікати** вже розписаного складу, якщо їхня роль — лише логічне групування. Кількість таких вузлів можна зафіксувати у `technical_parameters`.

### Як заповнювати поля компонента

- `name` — короткий термін **мовою основного тексту**, що дозволяє впізнати компонент; зберігати технічні коди й схемні позначення.
- `model` — **лише конкретна модель/маркування виробу** (`LM393`, `DS1302`, `SW-520D`, `S13V25F12`, `Portenta H7`). Позначення на електросхемі `R1`, `C1`, `D3`, `VT1`, `K1` — **не моделі**; якщо важливі для ідентифікації, записати в `name`, а `model: null`.
- `manufacturer` — тільки виробник, **якого можна прямо визначити з тексту/явної назви бренду**; не вгадувати за відомою моделлю або власними знаннями. Немає доказів → `null`.
- `role` — лише підтверджена роль **в конкретній статті**, стисло; якщо роль не наведена і не випливає безпосередньо з описаного з’єднання → `null`.
- Один фізичний елемент/тип із тією самою функцією — один запис; не дублювати через синоніми. Якщо конструкція одночасно містить плату та мікроконтролер на ній, обидва дозволені лише якщо джерело окремо описує їх як різні апаратні сутності (із чіткими ролями), а не двічі називає той самий об’єкт.

## 3. `technical_parameters`: що включати

**Параметр — числова, кількісна, конфігураційна або обмежувальна характеристика визначеного предмета.** Вона має перевірюване значення та чітку прив’язку до об'єкта.

### Включати

1. Напругу, струм, потужність, ємність, частоту, розмір, кількість деталей, часові інтервали, пороги/межі, діапазони, швидкість реакції тощо, **прямо наведені** в тексті, таблиці або коді.
2. Конфігураційні відповідності, наприклад `int data = 4` → цифровий пін датчика №4, `int motor = 7` → пін керування помпою №7; `SDA=A4` тощо. Явна відповідність «об'єкт ↔ контакт» обов’язкова.
3. Заявлені/цільові значення, лише **з правильною позначкою у `name`** (`desired range`, `заявлена потужність`, `бажана автономність`) — не описувати їх як перевірені виміри.
4. Точні умови або значення демонстраційного **експерименту**, якщо вони задають методику вимірювання/налаштування (`250` тестових значень, `0.05` швидкість реакції фільтра, `0.01–0.1` діапазон тестів).
5. Явно наведені прикладові *параметри налаштування*, коли вони пояснюють логіку системи (наприклад, **приклад** порогу попередження 50 г): у `name` обов’язково зазначити `приклад`, не маскувати під заводський або остаточно встановлений поріг.

### Не включати

- Будь-яке число, яке просто зустрілося в статті: рік публікації, випадкове число в прикладі сповіщення, випадковий ID, інвентарний номер, номер рисунка, номер кроку інструкції, порядкове число в реченні.
- Приклад **поточного показу** (`32 г` у повідомленні, `−170 г` як умовний негативний показ) — не стабільна властивість, налаштування або параметр експерименту.
- Загальні можливості на кшталт «може працювати автономно», «моніторить температуру», «працює в реальному часі» без конкретного вимірюваного значення або режиму, якщо їх не формалізовано як перелік режимів у самому джерелі.
- Пропозиції альтернативної системи, яка **не реалізована**. Технічні характеристики існуючої побічної інфраструктури — лише коли ця інфраструктура реально залучена до предмета статті, а не наведена як фон.
- Зіпсовані або двозначні числові дані, з яких неможливо достовірно відновити знак порівняння чи одиницю вимірювання. Винести в примітки, виключити зі scored fields.

### Як заповнювати поля параметра

- `subject` — **конкретний пристрій / вузол / конфігурація / експеримент**, до якого належить характеристика; збіг із назвою компонента бажаний, але не обов’язковий. Не приписувати число всій системі, якщо воно стосується лише одного вузла.
- `name` — конкретна фізична/конфігураційна характеристика та статус значення, коли суттєво: `measured`, `nominal`, `desired`, `example`, `typical`, `approximate`, `limit`. Мовою статті.
- `value` — **рядок**, що зберігає число/діапазон/знак нерівності/приблизність без домислення чи непозначеного округлення. Не подвоювати одиницю у `value` (для `12V` записати `"12"`, `"V"`). Для словесного `at least a dozen` зберігати обмеження, не перетворювати мовчки на доведений результат вимірювання.
- `unit` — одиниця, прямо наведена в тексті; якщо безрозмірне число (номер піна, кількість), `null`. Позначення одиниці зберігати близьким до джерела; співставлення `uA/µA/microamperes`, `В/V`, `секунди/s`, `кг/kilos` виконувати **під час оцінювання**, а не за рахунок вигадування нових відомостей.
- Для 2D-розмірів можна зберігати сполучене `"3,2 × 1,4"` з `"см"`, але правило оцінювання повинно розуміти еквівалентні десяткові роздільники та знаки множення.
- Не плутати `model`, позиційне позначення або артикул із виміряною числовою величиною.

## 4. Конфлікти та неповні дані

- **Не виправляти статтю за зовнішньою енциклопедією**. Якщо автор одночасно написав `lm7508` і `lm7805` для одного вузла, один компонент: `model: null`; обидва варіанти й контекст записати в **окремий анотаційний файл**, не створювати дві нібито встановлені деталі.
- Непевний `15 мА` в пошкодженому тексті HR-0068, де втрачено знак нерівності, не робити точною характеристикою. Якщо напрям межі не читається, параметр не оцінюємо.
- Не використовувати `null` замість явно відомого значення; але для непідтвердженої моделі/виробника ставити `null`, для відсутніх списків — `[]`.
- Якщо джерело саме помиляється, еталон відображає *що в ньому сказано*, а не «що має бути технічно правильно». Суперечність зафіксувати окремо, не вдавати впевненість.

## 5. Контрольні рішення для 10 статей

| Стаття | Застосування правил |
|---|---|
| HR-0743 | Підтримувані/вимірювані Portenta, Nicla, LiPo і вимірювальні засоби допустимі; `motion sensor` і `button` як лише приклади зовнішнього пробудження — виключити. Числа з таблиці струмів і `under 100 microamperes` — залишити з правильним контекстом. |
| HR-0244 | Залишити конкретні фактично використані Wemos, WS2812B, TTP223, тензодатчик, кріплення/роз’єми; `База системи` та `Вимірювальний пристрій` не дублювати як фізичні компоненти, якщо всередині вже розписано вузли. Поріг 50 г як **приклад** лишити; числа 32 г / −170 г з демонстраційного повідомлення як технічні параметри — виключити. |
| HR-0385 | Насос відхилений → виключити; MKR-плати лише з рубрик сайту → не приписувати як установлені. 1800 W наявного масиву не переносити в параметр системи поливу; масив включати лише якщо текст прямо пов’язує його функціонально із описаним контролером. |
| HR-0068 | 5 В, D2, 13, SW-520D та розміри — залишити; пошкоджений `15 мА` → окрема примітка, не scored parameter. |
| HR-0254 | SDA=A4, SCL=A5, CLK=6, DAT=7, RST=8 та інші явні значення — залишити. |
| HR-0212 | `LM393` — модель; `R1`, `C1`, `VT1`, `K1` — схемні позначення. Однорольові резистори `R1/R2/R3` можна об’єднати в один запис; інші з окремими ролями — залишити окремими. `≥4 год` — бажана автономність, не замір. |
| HR-0415 | Gripper і camera gimbal — лише можливі доповнення → виключити; `at least 200 meters`, `a dozen kilos` — бажані значення, а не виміряні показники. |
| HR-0207 | Один стабілізатор керування реле з конфліктними написаннями моделей → `model: null`; суперечність документувати. `15000uF 16V`, `0.3–0.5V` → зберегти. |
| HR-0227 | BMP280 + Arduino в реальній демонстрації; Raspberry Pi Pico згадано як контекст → не `components`. Коефіцієнти фільтра — параметри, але не апаратні компоненти. |
| HR-0187 | Arduino, датчик, помпа, перемички — складові; `data=4`, `motor=7` → два технічні параметри. Не додавати `Arduino IDE` без згадки у джерелі. |

## 6. Правило оцінювання і затвердження

1. Зіставляти компоненти та параметри за **сутністю + контекстом**, не за порядком у масиві і не лише за буквальним текстом.
2. Еквівалентні технічні написання (`uA/µA`, `UNO/Uno`, `1.2/1,2`) нормалізувати лише в оцінювачі. Не затирати вихідні значення.
3. Звіряти предмет параметра: `12 V` для батареї та `12 V` для живлення реле — **різні твердження**.
4. `Pydantic-valid` ≠ фактично правильний. Для Golden потрібні обидві перевірки.
5. Кожне сумнівне твердження фіксувати в окремому `golden_review_notes.md` із цитатою (короткий фрагмент або посилання на рядок) і рішенням.
6. Поки не виконана повторна звірка всіх записів із TXT, `annotation_status` зберігати як `needs_human_review`. Схему `v1`, промпт `v1`, оригінальні тексти і результати двох baseline-прогонів **не змінювати**.

**Версія правил:** `golden-annotation-rules-v1.0` (окремо від версії промпту). Зміни правил надалі оформляти новою версією, щоб порівняння моделей не використовувало непомітно змінений еталон.
